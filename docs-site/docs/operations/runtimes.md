# Runtime compatibility

How the package behaves in the PHP runtimes a Laravel application runs in, what was **verified in this repository and how**, and what was not. A runtime that was not run here is never called "supported": its row says what the code is designed to do and what remains to be tested.

All measurements: PHP 8.3.6 CLI (NTS) with `pcntl`/`posix`, libcurl 8.5.0 (nghttp2), OpenSSL 3.0.13, Laravel 13.43, Node 22 (the local HTTP/2 mock server in `tests/Support/H2Mock`), redis-server 7 (local), SQLite. Every count of connections and requests below was read from the mock server, not from the package.

## What "connection reuse" means here

`CurlTransport` keeps one persistent `curl_multi` handle per **pool key** (credential identity + endpoint role + environment + TLS/proxy profile + generation) in a **per-process** registry (`CurlPoolRegistry::process()`, a static). A connection is therefore reused only by later sends **in the same OS process**: across jobs of one queue worker, across requests of one long-lived HTTP worker. Nothing is shared between processes. The registry holds at most 32 pools by default (`transport.max_pools`; LRU; the evicted pool is closed), closes a pool idle longer than its `max_idle_seconds`, and abandons inherited pools when it notices a PID change. The manager keeps at most `mobile-push.connection_cache.size` (default 64) resolved connections and closes the pools of the one it evicts. See [transport.md](/reference/transport).

Reuse can be switched off: `mobile-push.transport.reuse` (`auto` by default, `on`, `off`). With `off` every send opens its own private pool (its own `curl_multi` handle and connection) and closes it when that send ends, so nothing is shared between concurrent callers and nothing is kept between sends. `auto` behaves as `on`, except for a send that starts while a coroutine runtime hooks curl (Swoole / OpenSwoole with `SWOOLE_HOOK_CURL` or `SWOOLE_HOOK_NATIVE_CURL` in its hook flags): that send runs as `off`. The price is one TCP + TLS handshake per send (measured on loopback: 200 sends → 200 connections instead of 1, about 3.1 ms instead of 0.6 ms per send) and, against APNs, many short connections, which Apple asks providers to avoid. Details in [transport.md](/reference/transport) ("Connection reuse").

### How to check a runtime yourself

```bash
vendor/bin/pest tests/Scenario/Runtime                  # transport: worker life, fork, many tenants, overlapping sends
vendor/bin/pest tests/Scenario/Laravel/Runtime          # queue:work, 200 runtime connections, request isolation, Octane sandbox, cache races
vendor/bin/pest tests/Scenario/Runtime tests/Scenario/Laravel/Runtime --group=slow   # soak variants
```

They need Node ≥ 18 (mock server), `pcntl`/`posix` (fork scenarios) and, for the redis case of the cache race, `redis-server` + `ext-redis` (skipped otherwise). They prove the package's mechanisms, not a runtime: to verify a runtime, run the same kind of scenario inside it (for Octane: a route that sends to a test endpoint, hit by many concurrent requests, counting the connections on the endpoint), and compare the server's counters with the expectations above.

## Scenario results

### 1. A queue worker that lives for a day

- Transport, one process: 2,000 batches of 5 requests on one pool key, a 300 ms pause every 250 batches → 10,000 requests received, **1 connection**, memory growth after 200 batches < 256 KiB, open descriptors equal. Soak (`slow`): 20,000 batches / 100,000 requests, same results.
- Idle longer than `max_idle_seconds` (1 s in the test) → exactly **2** connections in total, the old one closed.
- The server closes the idle connection after each of 5 jobs → 20/20 requests answered, 5 connections (one reconnect per close, never more), no failure.
- Laravel: real `queue:work` loop on the `database` queue, 2,000 `SendPushJob`s → see the matrix.

### 2. Fork

- **(a) Child sends while the parent sends** (child ends with `SIGKILL`): the child's registry resets for its PID (`CurlPoolRegistry::inheritedCount()` = 1), it opens **its own** connection, the parent keeps **one** connection before, during and after; each process receives exactly the answers to its own request ids (the server echoes the request path in the body); 95/95 requests received and processed, 2 connections in total.
- **(b) Residual risk, reproduced**: when a child **exits normally**, PHP's shutdown frees the inherited curl handles; libcurl then reads from and writes a TLS `close_notify` on the socket the parent still uses.
  - parent idle at that moment: its connection is closed (server sees 0 open); the next send reconnects transparently, 3/3 answered;
  - parent with **3 requests in flight**: all 3 come back `Unknown` (errno 55 `SSL_write: SSL_ERROR_ZERO_RETURN` / errno 65 `bad record mac`), **although the server processed all 3** (→ `OutcomeUnknown`, possible duplicates if retried). The next send reconnects.
- **Can the transport prevent it? No safe fix exists in PHP.** The damage is done by `curl_multi` free handlers during the child's shutdown, which run for every live object even in fast shutdown, before and regardless of any code of the package; libcurl offers no option to drop a connection without the TLS shutdown, and PHP cannot close a raw descriptor in the child only (that would need FFI). A shutdown function that kills the child would change the child's exit status and skip the application's own shutdown work. The registry already never reuses or closes inherited pools itself.
- **Recommended patterns** (both pinned by tests): close the pools before forking (`$transport->close()` / `MobilePush::flush()`): the parent then sends on a fresh connection; or end children with `posix_kill(getmypid(), SIGKILL)` after their work. Best: do not send from a process that forks; let each worker open its own pools.
- Laravel `queue:work` does not fork; `queue:listen` and the framework's process helpers use `proc_open` (read in source). Laravel's `Concurrency` **fork** driver (spatie/fork) does fork and its children exit normally: do not use it in a process that has sent pushes.

### 3. Two hundred tenants on one worker

- Transport: 200 pool keys in sequence, then all again: the server never saw more than **32** open connections (the registry limit) after each send, 400 connections in total (an LRU cycle longer than the limit reconnects every revisit), 368 evictions, each evicted pool closed (server-side close observed), process sockets = 32, descriptors and memory flat between the first and the second pass. A working set under the limit (8 tenants × 3 passes) → 8 connections, no eviction. Soak (`slow`): 10 passes.
- Laravel: 200 tenants registered at runtime (`MobilePush::register(..., scope)`), each with its own APNs key, served twice: with `connection_cache.size` 16 the server never saw more than **16** open connections (the manager closes the pools of the drivers it evicts); with the default 64 above the registry's 32, never more than **32**. 400/400 accepted, memory growth on the second pass < 512 KiB, descriptors equal; `MobilePush::flush()` closes all.
- The registry limit (32) is configurable: `transport.max_pools` (env `MOBILE_PUSH_TRANSPORT_MAX_POOLS`, an integer of at least 1). With the default value `SendingModule` builds `new CurlTransport` on the shared per-process registry. With any other value it gives the `Transport` singleton **a dedicated registry** of that size: its pools are no longer shared with other `CurlTransport` instances of the process, and live as long as that singleton. Raise it when one process serves many distinct connections or tenants (one pool per provider endpoint, credential and settings); the numbers measured above are for the default of 32 and have not been repeated for other values.

### 4. Overlapping sends in one process (simulated coroutines)

Two "requests" (PHP Fibers) each iterate their own `send()` on the **same pool** and yield to each other after every answer, so the generators overlap on one curl multi handle:

- 40 + 40 requests interleaved (the server received them alternating): every answer reached the generator that sent it, nothing lost or duplicated, one connection.
- One generator abandoned after 3 answers with requests still in flight: its streams were reset (`RST_STREAM`, counted by the server), the other finished 30/30 correctly, the connection survived, the next send was correct.
- A request suspended forever keeps its pool "in use" (never evicted; `close()` defers until release); destroying its Fiber runs the generator's cleanup and the deferred close happens.
- **Defect found and fixed** (`CurlPool::perform()`): while one generator waited for its answer and another, suspended generator had completions queued, the waiting generator skipped `curl_multi_select()` and spun on `curl_multi_exec()` for the whole wait (measured 0.15 s of CPU for a 0.4 s wait). The wait is now skipped only when the caller itself has a completion to take (measured < 1 ms of CPU). Pinned by `OverlappingSendsTest`.
- Safe rule: concurrent sends on one pool are correct **when the switching happens between pushes** (Fibers, generators, a consumer starting a second send inside the first). Switching **inside** a curl call (Swoole curl hooks) on a **shared** pool is not supported and crashes the worker. `transport.reuse = off` (or `auto`, the default, when a curl hook is detected) gives every send its own pool, so two coroutines never drive the same `curl_multi` handle: measured under Octane on Swoole 6.2 with every hook on, the transport then never failed (one connection per send), while some concurrent requests still failed in Octane's shared application container. Under such a runtime send from queue workers.
- Reuse off, the same Fiber simulation (`tests/Scenario/Transport/ConnectionReuseTest.php`): two interleaved sends of one pool key arrived on **two** server-side sessions, each sender's requests on its own one, every answer to its sender; one abandoned half-way with requests in flight did not disturb the other; a send suspended forever held only its own connection, closed when its Fiber was destroyed; after every case the server saw **0** open connections and the transport 0 private pools.

### 5. State between requests (Octane-style)

**Shared app** (the app booted once, the same container for every request — a queue worker, or an Octane worker where the manager was resolved at boot), 40 tenants in a row, each request with `scopeUsing()`, a tenant resolver, its own key and device (`RequestIsolationTest`): every request sent only with its own scope, its own team/key JWT, to its own device; the `PushBatchCompleted` event and the log record carried its scope; the log buffer was empty after `terminate()`; one bearer per tenant, never another tenant's. A tenant whose key is refused trips **its** auth breaker only (shared store, keyed by account): the next tenant is accepted, the refused tenant stays off the wire in its next request (`Skipped` / `CircuitOpen`).

Pinned limitations of a shared manager (the API is process-level, not request-level). The recommended pattern stays **configure once, at boot**; each of these has an undo for the cases where that is not possible:

- a request that does not call `scopeUsing()` **inherits the previous request's scope** → call `scopeUsing()` once at boot with a resolver that reads the current request (`fn () => app(CurrentTenant::class)->id ?? 'default'`). To remove a resolver, call `MobilePush::scopeUsing(null)` or `MobilePush::forgetScopeResolver()` (the scope then falls back to `mobile-push.scope`);
- `eligibleUsing()` called per request **accumulates**: every earlier check keeps running in later requests (`FallbackPolicy::allowUsing()` of the notifications module has the same shape) → register checks once, at boot. To remove one, pass the same callable to `MobilePush::forgetEligibility($check)` (it returns how many registrations it removed; a closure must be the very same instance). `FallbackPolicy::forget($check)` (same rules, returns the count removed) and `FallbackPolicy::flush()` (removes all) do the same for the fallback checks registered with `allowUsing()`;
- `register()` keeps every runtime connection (with its key material) for the life of the process → for many tenants use `resolveConnectionUsing()` (resolved on demand, the drivers bounded by the cache). To drop one, call `MobilePush::unregister($name, $scope)` (it also drops the cached driver and closes its pools; a configured connection of the same name is used again from the next send); to drop a connection resolver, `MobilePush::forgetConnectionResolver()` (drivers already resolved through it stay cached until `forgetConnection($name)` or `flush()`).

**Octane sandbox** (`OctaneSandboxTest`; Octane's mechanism reproduced: `clone $app` per request, the clone bound as container and facade root, cloned config, `terminate()` at the end; Octane itself not installed):

- A manager resolved during the request lives only in that request: nothing set by one request was seen by the next (scope, runtime registrations). Connections still reused: 20 sandboxed requests → **1** connection, because the transport each request builds uses the per-process registry; one provider token for all of them when the cache manager is warm (Octane warms `cache` by default).
- With the `array` cache store resolved per request, **every request minted a new APNs token** (3 requests → 3 tokens): Apple rejects frequent token updates (`TooManyProviderTokenUpdates`). Use a shared store.
- A manager resolved at boot (e.g. by calling `MobilePush::resolveConnectionUsing()` in a service provider) is shared by every sandbox: the limitations of a shared manager apply.
- **Defect found and fixed (Logging module)**: the terminating hook used to look at the application that booted the module, where a `SinkManager` resolved inside a sandbox is not visible, so the buffered records of a sandboxed request were lost with the clone. It now flushes the `SinkManager` of the application being terminated (the sandbox); a test pins it.

### 6. Cache-backed coordination across real processes

Eight PHP processes (`proc_open`), each booting the application, start at the same instant on a **cold** store, ask for the APNs provider token and take 30 permits each (240 asked) from a rate limiter of 100 with a frozen clock (`CacheCoordinationTest`):

| Store | Exercised | Token | Permits granted |
|---|---|---|---|
| redis (real `redis-server`, `phpredis`) | yes | one token used by all 8 (1–8 signatures: on a cold store every process may sign, the compare-and-swap keeps one) | exactly 100 |
| database (shared SQLite file, WAL) | yes | one token | exactly 100 |
| database on a server engine (MySQL 8.4, MariaDB 11.4, PostgreSQL 17; eight connections) | yes, in CI (`databases` job) | one token | exactly 100 |
| file (shared directory) | yes | one token | exactly 100 |
| memcached 1.6 (`ext-memcached`) | yes, in CI (`backends` workflow) | one token | exactly 100 |
| dynamodb (DynamoDB Local, `aws/aws-sdk-php`) | yes, in CI (`backends` workflow) | one token | exactly 100 |

With the store **unreachable**: each process signs and uses its own token (the designed local fallback), and the rate limiter and the circuit breakers **fail open**: they cannot coordinate without the store, so they stop limiting instead of stopping the sends (every take is granted, nothing throws; measured with 8 processes against a port with nothing listening). After a failure the cache backend is left alone for 5 seconds, so a dead cache server does not cost a connection timeout on every send, and a warning is logged at most once a minute per process. A store that is alive but so contended that 50 compare-and-set attempts lose is a different case: nothing is granted and the destinations come back `Deferred` (`quota_exceeded`), never as an exception.

This was a **defect found and fixed** here: before the fix an unreachable store surfaced as `RuntimeException('Guard state is too contended to update.')` thrown out of the send.

A second **defect found and fixed** by the same scenario, on the `database` store with **MySQL**: Laravel's database lock takes a lock with an `INSERT` and, when the row is there, an `UPDATE` of the expired one. With eight processes after the same lock, MySQL answers some of those statements with a deadlock (error 1213, SQLSTATE 40001) instead of making them wait. The guard store read that answer as an unreachable backend and failed open for five seconds in that process: 175 permits were granted from a budget of 100 on MySQL 8.4 (124 to 129 in four of six runs on MySQL 8.0). A deadlock, a serialization failure or a lock wait timeout reported by a database-backed store now counts as "the lock was not taken": the compare-and-set is lost and retried, the store stays available, and a deadlock while releasing a lock is retried so the lock is not left behind. After the fix eight of eight runs granted exactly 100. MariaDB 11.4 and PostgreSQL 17 did not show the deadlock. The frequency cap and the badge counter use the same store and were exposed to the same defect.

## Not verified

- AWS Lambda/Vapor (needs an AWS account), PHP-FPM (not run; the conclusion follows from the design). Octane on RoadRunner, Swoole, OpenSwoole and FrankenPHP is run in CI with sequential requests and with eight requests at a time, simulated pushes and a local HTTP/2 mock server on the wire: what a **real provider** connection does across their requests, and sustained production load, were not measured. Swoole's **coroutine hooks** were run and are **not supported** for sending from HTTP workers (see the table): the transport holds with reuse off, Octane's shared application does not. Horizon is run with simulated sends only.
- A worker running for real hours: idle periods were simulated with short pauses and a 1-second `max_idle_seconds`; the libcurl default for idle reuse (118 s, overridden by the transport) and TCP keepalive were measured by the transport author (see transport.md), not re-measured here.
- `queue:work` was run in the test process through `Artisan::call()` (the real worker loop), not as a separate `php artisan` process.
- The cache stores against production services: memcached and DynamoDB were run against a local memcached and DynamoDB Local, Redis against a local `redis-server`, the `database` store against the MySQL, MariaDB and PostgreSQL containers of the CI job. None of them is a production deployment (replication, a managed service, a network in between).
