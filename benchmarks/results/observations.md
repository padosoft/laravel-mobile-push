## Observations (written by hand for the run above; not regenerated)

All of these are about this machine on the day of the run, which was shared and busy (load average about 19-21 on 4 cores for the whole session). Wall-clock figures swung by 20-90% between repeated runs of the same command, so conclusions below rely on CPU per request, memory, connection counts and recorded behaviour, which were stable, and on throughput only where ranges do not overlap.

**Cost of the pipeline.** The full `Sender` pipeline spends more CPU per request than the bare transport: about 0.066-0.069 ms/req (APNs, FCM, no delay) against 0.042 ms/req for the raw transport, and 0.073-0.085 against 0.054 with a 20 ms server delay. The extra is roughly 0.03 ms of PHP CPU per notification for compile, guards, bearer, classification, retry planning and result objects. With a 20 ms server delay the pipeline reached 2,499 req/s (range 2,297-2,723) for APNs and 3,003 (2,633-3,049) for FCM versus 3,005 (2,749-3,193) for the raw transport at window 100: the pipeline was slower in this run, and the APNs pipeline noticeably so; the tables flag where the spread exceeded 15%. At zero delay the Node mock and the PHP process compete for the same cores and the ranges overlap.

**Mixed outcomes.** 5% non-accepted outcomes (3% 410, 1% 400, 1% 500) cost about 0.073 ms/req against 0.069 for the all-accepted control (same run conditions); the difference is within the noise of the CPU measure. The per-run outcome counts (600 unregistered, 200 rejected, 200 deferred, 19,000 accepted per 20,000) match the script exactly, and the server received each request once: nothing was retried inline.

**Warm versus cold.** Over 30 runs of a single request, the median request took 0.7 ms (range 0.5-1.9) on a warm pool and 6.6 ms (3.2-11.1) when it had to open the connection first (TCP + TLS 1.3 + HTTP/2 against a local server); client CPU for that request was about 2 ms. Over 20,000 requests that setup is invisible in throughput. Real providers add network round trips to every handshake; this number is a local floor, not an estimate.

**Window.** With a 20 ms server delay and one connection, throughput followed window / delay at small windows (window 10: 413 req/s; 50: 1,938; 100: 3,993, against theoretical 500, 2,500, 5,000) and stopped scaling between 250 and 500 (8,436 at 250; 7,433 at 500, range 6,511-8,999) while p50 latency doubled from 28 ms to 59 ms: beyond about 250 in flight the client or the mock is the limit on this machine and extra requests only queue. Memory grows with the window (peak 0.3 MiB over start at 10-250, 2.0 MiB at 500).

**Connections.** When the peer allows 1000 concurrent streams, 1, 2 and 4 connections gave the same throughput within the noise (8,066 / 7,447 / 8,196 req/s). When the peer advertises 100 streams and the window is 500, throughput rose with the connection count (3,826 -> 6,488 -> 8,338 req/s) and p99 latency fell (475 ms -> 228 -> 131). The server counted exactly 1, 2 and 4 connections. This supports the transport's rule "keep window <= peer limit x connections", not any particular real peer limit.

**Large batches.** 100,000 and 1,000,000 destinations from a generator ran with PHP memory between 6.6 and 7.2 MiB for the whole run (range over the second half: 0.25 MiB in both runs; peak 2.5 MiB over the starting usage); the 1,000,000 run did not use more memory than the 100,000 run. 0 transport errors, 1 connection, all accepted, 5,774-6,735 req/s.

**Many tenants.** 200 pool keys in one process with the default registry limit (32): the registry stayed at 32 pools, the server never saw more than 32 open connections and the process never held more than 102 file descriptors (6 at the start and after `close()`); 168 pools were evicted. With limit 1000 the process held 606 descriptors and 200 server connections at the end. PHP memory looks like it grows with the number of tenants (4.2 to 7.7 MiB) but returns to the starting level after `gc_collect_cycles()` (3.81 MiB vs 3.78 MiB at start): closed pools leave cycles that wait for the collector. After the garbage collection the registry limited to 32 holds about 0.8 MiB more than at start, the unbounded one about 4.3 MiB. Each new connection cost about 2.4 ms of client CPU (0.49 ms/req over 5 requests).

**Against pushok 0.19.1** (same notifications, mock, delay and concurrency; hostname verification off for pushok only, see above):

- CPU per request: pushok 0.043 / 0.055 / 0.069-0.070 ms (zero delay / window 100 + 10 ms / window 20 + 10 ms); this package's raw transport 0.041 / 0.052 / 0.070; this package's full pipeline 0.072-0.073 / 0.080-0.085 / 0.103-0.107. The pipeline does work pushok does not do (compile, guards, classification, retry planning).
- Throughput: ranges overlap heavily and spreads were 22-91%, so no ordering of pushok and this package's raw transport can be claimed. At window 20 (tightest runs) the medians were 1,434 req/s (raw transport), 1,496 and 1,507 (pushok), 1,270 and 1,282 (full pipeline), ranges 1,204-1,674; the full pipeline was lower than the others in that table.
- Memory: pushok holds every notification and response in memory until `push()` returns: peak 7.0 MiB over start for 5,000 notifications (0.06 MiB for the raw transport, 1.4 MiB for the pipeline with lazy input and a cursor report). That scales with N for pushok; this package stays flat (see large batches).
- Connections: both used one connection with `window` 100 and with 20; pushok's default (`autoCloseConnections=true`) opened one new connection per `push()` call, as designed.
- Behaviour: when a request is processed and the connection is then destroyed, on a connection that had already carried a request, **pushok returned HTTP 200 for it and the server had processed the push twice** (libcurl re-sent the in-memory body on a new connection); this package reported `outcome_unknown` and the server received it once. As the first request on a new connection, pushok threw `Exception: Send failure: Broken pipe` (and, in a batch, no responses at all were returned for any of the five notifications, although the server processed all five); this package returned one result per destination: the first one accepted and four `outcome_unknown` (the in-flight siblings of the dropped connection, which the server did process). For a 503 both returned the status without retrying (pushok: status 503, reason ServiceUnavailable; this package: `deferred`/`provider_unavailable` with a next attempt planned); a 410 gave pushok status 410 with the timestamp as a string and this package `rejected`/`destination_unregistered` with `invalidate` and the timestamp in milliseconds. When the connection was cut in the middle of the response body, pushok returned status 200 and this package `outcome_unknown`.

**Defaults.** On this machine the measurements do not argue against `window = 100` and `maxConnections = 1`: 100 in flight reaches about 80% of the window/delay limit at 20 ms, memory is small, and one connection is as fast as four as long as the window does not exceed the peer's stream limit. They also show headroom up to a window of about 250 locally (twice the throughput at 20 ms), which is a local, mock-based result: the provider's real stream limit, latency and throttling decide whether it is useful, and a larger window also puts more requests in `Unknown` when a connection is lost. No change of defaults is justified by these data alone.

**Not measured.** Real APNs/FCM latency, throughput, stream limits and throttling; behaviour under packet loss or slow links; FPM/Octane/queue-worker processes; Redis/database-backed guard or token stores; a second PHP/libcurl version; token signing cost per request (tokens are cached for the run); other libraries; what pushok does with a window above its own default of 20 beyond the settings shown (it was run at 20 and 100).
